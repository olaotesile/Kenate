I. PREFACE: THE EVOLUTION OF ROBOTIC PROGRAMMING
================================================================================

The Kenate framework was developed by Euretix Labs in 2025 as a direct response to the fragility of traditional robotic software. For decades, developers relied on monolithic control loops dominated by "Spaghetti Logic"--endless chains of if-else statements that became impossible to debug as systems evolved.

Kenate represents a paradigm shift. It treats robotic behavior as a set of isolated, high-performance modules. By replacing "scripts" with "states," Kenate allows for the creation of autonomous systems that are modular by design and harder to break by accident.

================================================================================
II. THE UNIQUE VALUE PROPOSITION
================================================================================

Why choose Kenate over standard alternatives?

1. THE 1000HZ DETERMINISTIC HEARTBEAT
Most programming languages, including Python, suffer from "jitter." This means their timing is unpredictable. For a robot moving at high speeds, a 50-millisecond delay in "thinking" can lead to a catastrophic collision. 

Kenate uses a dedicated C++ Kernel that targets 1000Hz by default. This 1-millisecond target interval provides the "heartbeat" required for professional-grade motion control.

2. THE HYBRID KERNEL EXCLUSIVITY (C++ AND PYTHON)
Kenate allows you to write high-level logic in Python while maintaining the performance of C++. The Engine handles the technical parts -- memory management, high-speed sensor polling, and motor timing -- so you can focus entirely on the robot's intelligence.

IV. THE DEVELOPER WORKFLOW: "INIT, RUN, ANALYZE"
================================================================================

Professional robotics follows a disciplined lifecycle. Kenate enforces this through its CLI.

STEP 1: INITIALIZATION
$ kenate init MyFirstRobot
$ cd MyFirstRobot

This creates the EURETIX STANDARD directory structure:
- configs/: Hardware profiles and safety thresholds (JSON).
- src/: Your custom mission-specific Python logic.
- examples/: Reference missions and verify-install templates.
- .kenate_logs/: High-frequency Black Box telemetry data.
- build/: C++ binaries and the high-speed Hardware Bridge.

STEP 2: THE AUTONOMOUS MISSION
Missions are built using ATOMIC STATES. You define how the robot behaves in isolation, and the engine handles the high-speed execution.
$ kenate run examples/hello_robot.py

STEP 3: POST-MISSION ANALYTICS
After every mission, Kenate allows you to "Rewind the Clock."
$ kenate analyze

This command parses the Black Box logs to provide:
- MISSION DURATION: Exact timing of the flight or run.
- THERMAL PROFILE: Heat maps of the CPU and motors.
- ENERGY CONSUMPTION: Battery drain percentages.

V. THE KENATE STANDARD LIBRARY (ENTERPRISE GRADE)
================================================================================

Kenate ships with a built-in suite of behaviors called the Standard Library. Each module is optimized for the 1000Hz Kernel.

1. WAIT STATE (WaitState())
Purpose: Provides precision timed pauses without blocking the control loop.

2. SEQUENCE STATE (SequenceState())
Purpose: Chains multiple behaviors into a single autonomous flow.

3. PID CONTROLLER STATE (PIDState())
Purpose: Industry-standard math for smooth, precise motor positioning.

4. WATCHDOG STATE (WatchdogState())
Purpose: A background safety guardian that monitors system health.

5. BLACK BOX LOGGER (BlackBoxLogger())
Purpose: Captures high-frequency (1000Hz) telemetry data for analysis.

6. TERMINAL VISUALIZER (TerminalVisualizer())
Purpose: A live-updating console dashboard for mission monitoring.

VI. FULL API CATALOG (THE BRIDGE)
================================================================================

This section provides a formal list of every class and function available within the core 'kenate' package.

1. THE ROBOT CLASS (kenate.Robot())
The high-level manager for mission execution.
- create_state(name, class): Registers a behavior.
- start(): Commences the mission heartbeat.
- stop(): Terminates the mission safely.

2. THE BASE STATE CLASS (kenate.BaseState())
The foundation for all custom behaviors.
- on_enter(): Executes once when the state becomes active.
- on_update(): Executes every millisecond (The Heartbeat).
- on_exit(): Executes once when moving to a new state.
- get_height_sensor(): Returns current altitude/height.
- get_distance_sensor(): Returns obstacle proximity.
- get_battery_level(): Returns battery percentage.
- get_system_temperature(): Returns core temperature (Celsius).

VII. SAFETY PROTOCOLS AND OVERRIDES
================================================================================

Professional robotics requires "Safe Failure" design.

1. THERMAL MANAGEMENT
If the motor core or processor exceeds the threshold defined in your Robot Profile (e.g., 85C), the system should transition to a Safety State immediately.

2. SIGNAL INTEGRITY
Autonomous drones rely on signal strength for overrides. Kenate recommends a threshold of 20%. Below this, the robot should enter Return To Home (RTH) sequence.

3. KERNEL HALT
If the logic fails entirely, the C++ Kernel kills power to all motors to prevent property damage.

X. DEVELOPER DEEP DIVE: ARCHITECTURE AND INVENTORY
================================================================================

This section provides a clinical, high-fidelity breakdown of the Kenate v1.0.6 ecosystem for senior robotics engineers.

1. THE KENATE MODULE INVENTORY (kenate.*)
The framework consists of 5 core sub-modules providing 15+ specialized methods:

- kenate.stdlib (THE BRAIN):
  - WaitState(duration): Non-blocking time management.
  - SequenceState([states]): Automates behavior transitions.
  - PIDState(p, i, d, t): .calculate(current) -> error correction.
  - BlackBoxLogger(): .log(state_name, sensors) -> 1000Hz telemetry.
  - WatchdogState(timeout): .heartbeat() and .check_health().

- kenate.diag (THE DASHBOARD):
  - TerminalVisualizer(id): .render(state, sensors) -> Real-time console UI.

- kenate.hal (THE HARDWARE):
  - GPIOMotor(name, pwm, dir): .set_velocity(val) -> PWM signal mapping.
  - GenericSensor(name, addr): .read_value() -> Hardware address polling.

- kenate.config (THE BLUEPRINT):
  - ConfigLoader(): .load(path), .get(key), .validate([required_keys]).

- kenate.analyze (THE ANALYTICS):
  - analyze_log(path): Parses CSV data into a Performance Profile.

2. ROBOT PROFILE SCHEMA (JSON)
The Standard Profile requires these top-level keys for safe deployment:
- ROBOT_ID: (String) Unique identifier for the machine.
- SAFETY: (Object)
  - MAX_TEMP: (Float) Maximum core temperature before lockdown.
  - MIN_BATTERY: (Int) Lower bound for mission abort.
- PARAMETERS: (Object) Global constants (e.g., "MAX_WHEEL_SPEED", "GAINS_P").

3. KERNEL EDGE CASES: THE C++ CATCH-UP PROTOCOL
Kenate is a deterministic framework. If your Python 'on_update()' logic takes >1ms (a "Tick Overrun"), the C++ Kernel follows the "Catch-Up Protocol":
- Detection: The engine detects that 'next_wake' has already passed.
- Action: It skips the 'sleep' command entirely and executes the next tick IMMEDIATELY.
- Result: The system does not "drop" ticks, but it will temporarily run at maximum CPU speed until it has caught back up to its 1ms schedule.
- Pitfall: Never use 'time.sleep()' or blocking I/O inside 'on_update()', as this forces a permanent Tick Overrun.

4. ADVANCED PATTERN: THE OBSERVER WATCHDOG
Instead of writing safety logic inside every state, Kenate engineers should instantiate a 'WatchdogState' and 'BlackBoxLogger' as attributes of their primary Task state. This separates the "Mission Goal" from the "System Safety," ensuring high-frequency logging occurs even if the goal state encounters an error.

--------------------------------------------------------------------------------
MASTERCLASS 1: AUTONOMOUS DELIVERY ROBOT (The Warehouse Suite)
--------------------------------------------------------------------------------

OVERVIEW: A mission-critical system that handles battery audits, collision avoidance, and thermal monitoring in a single autonomous flow.

PHASE 1: INSTALLATION & PROJECT BOOT
$ pip install kenate --no-cache-dir
$ kenate init WarehouseBot
$ cd WarehouseBot

PHASE 2: IMPLEMENTATION (src/delivery_bot.py)
Logic Breakdown:
1. SafetyLayer (SafetyLockdown): An "Atomic State" that only exits when the system is safe.
   Rationale: Safety should never be a branch in a mission script; it should be a destination. 
2. BatteryCheck: Performs a pre-flight energy audit. 
   Rationale: We transition to 'SafetyLockdown' BEFORE moving, preventing "Dead-in-the-Water" scenarios.
3. Navigation (The Heartbeat Loop):
   - SENSE: Polls 'get_distance_sensor()' every 1ms.
   - THINK: If distance < 30cm, we use 'transition_to' to pause at a 'WaitState'.
   - ACT: Uses 'TerminalVisualizer' to provide a live-updating dashboard for warehouse technicians.

PHASE 3: MISSION ANALYSIS
$ kenate run src/delivery_bot.py
$ kenate analyze
Rationale: The 'analyze' report provides the "Receipt of Mission," proving the thermal and energy efficiency to the client.

MASTERCLASS 2: HEXAPOD BIOMIMETIC GAIT (The Tripod Crawler)
--------------------------------------------------------------------------------

OVERVIEW: Coordinating 6 legs (18+ motors) requires perfect synchronization. We use the 1000Hz heartbeat to generate smooth mathematical waves.

PHASE 1: THE MATHEMATICAL GAIT (on_update)
Rationale: Traditional walking scripts use 'sleep()' commands, which cause the legs to stutter. Kenate uses a "Wave Generator" pattern.

Code Logic:
- Global Clock (0.001s increments): We increment a cycle time by exactly 0.001 per tick.
- Sine Wave Oscillators: We use math.sin() to calculate the height of 'Tripod A' and 'Tripod B'.
- Tripod Pattern: Legs 1,3,5 (Group A) lift while Legs 2,4,6 (Group B) push.

PHASE 2: LIVE STABILITY STREAMS (The Dashboard)
Rationale: Walking robots are prone to "Dragging." We use the 'get_height_sensor()' during every single millisecond update. If the ground distance drops below 2cm, the robot recognizes a "Chassis Drag" and adjusts torque.

PHASE 3: GAIT ANALYSIS & REWIND
By reviewing the Black Box logs, engineers can see the "Wave Synergy" between the legs. If one leg is lifting too late, it will appear as a "Jitter Spike" in the analytics report.
